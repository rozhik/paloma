# Формат файлу `.picasa.ini` — специфікація для reverse engineering

Документ описує формат службового файлу `.picasa.ini`, який Google Picasa 3.x створює в кожній папці з фотографіями. Мета — дати достатньо деталей, щоб написати сумісний парсер (і, у перспективі, writer) для Paloma.

Загальний огляд неруйнівного редагування — у [06-storage-and-metadata.md](06-storage-and-metadata.md). Цей документ його уточнює і в разі розбіжностей має пріоритет.

## 0. Джерела даних і рівень достовірності

Специфікацію складено за реальним корпусом файлів (жовтень 2026) і звірено з публічними джерелами (див. §12).

| Показник корпусу | Значення |
| :--- | :--- |
| Файлів `.picasa.ini` | 201 (з них 2 порожні, 0 байт) |
| Секцій файлів (`[IMG_….JPG]`) | 4 747 (4 746 `.jpg`, 1 `.bmp`) |
| Секцій альбомів (`[.album:…]`) | 526 (28 унікальних альбомів) |
| Секцій `[Picasa]` | 93 |
| Секцій `[Contacts]` / `[Contacts2]`, ключів `faces=` | 0 — у корпусі відсутні |

Додатково знайдено в інших каталогах з фото (§9): 2 файли `Picasa.ini` (Picasa 3.0, 2008, папки експорту), 1 файл `.picasaoriginals/.picasa.ini` і 5 файлів `Thumbs.db` (Провідник Windows XP).

Позначки достовірності:

* ✅ **перевірено** — підтверджено на всьому корпусі (скриптом або на реальних зображеннях);
* 📚 **підтверджено джерелом** — збігається з корпусом і з незалежним публічним описом;
* 🔶 **гіпотеза** — узгоджується з даними, але семантику не перевірено;

Основні зовнішні джерела: [gist fbuchinger «.picasa.ini decoded»][gist] (Picasa 3.8, з коментарями), [специфікація PicasaPy][picasapy] (reverse engineering `Picasa3.exe` 3.9, угорською), [picasa3meta][p3m] / [metaSave][metasave] (vosbergw).

## 1. Фізичний формат файлу

| Властивість | Значення | |
| :--- | :--- | :--- |
| Ім'я | `.picasa.ini`. Ранні версії Picasa писали `Picasa.ini` ([PicasaPy][picasapy]) — підтверджено файлами Picasa 3.0 від 2008 року (§9.1). Парсер має шукати обидва імена без урахування регістру. На Windows файл має атрибут «прихований» | ✅ / 📚 |
| Кодування | UTF-8 **без BOM** | ✅ / 📚 |
| Кінці рядків | `CRLF` (`\r\n`), у тому числі після останнього рядка | ✅ / 📚 |
| Порожній файл | Допустимий (0 байт) — означає «немає даних» | ✅ |
| Коментарі (`;`, `#`) | Не зустрічаються. `;` усередині значень — звичайний символ-роздільник | ✅ |
| Порожні рядки | Не зустрічаються, але парсер має їх пропускати | ✅ |
| Пробіли навколо `=` | Відсутні. **Пробіли у значенні значущі** (`name= птицы  Украины`, `location= `) — не робити `trim()` | ✅ |
| Дублікати секцій у межах файлу | Не зустрічаються | ✅ |

**Про кодування.** Picasa не використовує Win32 API `GetPrivateProfileString`/`WritePrivateProfileString` для цього файлу: ці функції працюють лише з ANSI (кодова сторінка системи) або UTF-16, а не з UTF-8 ([WelliSolutions][welli], [MS Q&A][ms-utf8]). Отже, Picasa має власний парсер. У коментарях до [gist][gist] зазначено, що на англомовній Windows файл в UTF-8, а для інших мов «може знадобитися інше кодування». У корпусі (українська/російська Windows, кирилиця) — чистий UTF-8, тож це застереження не підтверджується. Для надійності: якщо файл не декодується як UTF-8, пробувати `windows-1251`/системну ANSI-сторінку. 🔶

**Секція `[encoding]`.** У `Picasa3.exe` є рядки `[encoding]` / `utf8=1`. PicasaPy знайшов їх у 0 з 859 реальних файлів і стверджує, що вони пишуться лише при експорті «backup to disc». Наші файли це уточнюють: `[encoding]` / `utf8=1` є в обох `Picasa.ini` папок **експорту** Picasa 3.0 (§9.1). Отже, секція з'являється щонайменше на шляху Export, а не лише Backup. У звичайних папках її немає (0 з 201). Читати — допускати, при записі — не додавати. ✅ / 📚

> ⚠️ Python `open()` у текстовому режимі та подібні API нормалізують `\r\n` → `\n`. Читайте файл як байти або явно розбивайте за `\r\n`, щоб writer міг відтворити оригінальні кінці рядків.

### Граматика (EBNF)

```ebnf
file      = { section } ;
section   = header , { entry } ;
header    = "[" , section-name , "]" , CRLF ;
entry     = key , "=" , value , CRLF ;
key       = 1*( any-char-except "=" CRLF ) ;   (* чутливий до регістру: P2category; бувають ключі з пробілами *)
value     = *( any-char-except-CRLF ) ;        (* може бути порожнім або з пробілами *)
section-name = "Picasa" | "Contacts" | "Contacts2" | "encoding" | "photoid"
             | ".album:" , token
             | file-name ;                     (* ім'я файлу в цій самій папці *)
```

Ключі можуть містити пробіли й не-ASCII символи, напр. `BKTag All Pictures-backuphash=10005` ([gist][gist], коментарі). ❔

**Дублікати.** У корпусі не зустрічаються. Для класичних Windows INI задокументовано: при повторі ключа в секції повертається **перше** входження, а значення з повторної секції ігноруються ([WelliSolutions][welli]). Оскільки Picasa має власний парсер, це не гарантія її поведінки, але як дефолт Paloma варто взяти саме «перше входження перемагає». 🔶

## 2. Типи секцій

### 2.1. `[Picasa]` — метадані папки

```ini
[Picasa]
name=2020-04-26
category=Folders on Disk
```

| Ключ | Приклад | Опис | |
| :--- | :--- | :--- | :--- |
| `name` | `2020-04-26` | Відображувана назва папки в Picasa (може відрізнятися від імені директорії) | ✅ |
| `category` | `Folders on Disk` | Категорія в лівій панелі | ✅ / 📚 |
| `P2category` | `Folders on Disk`, `Projects (internal)`, `Exported Pictures` | Категорія для Picasa 2+. `Projects (internal)` — службові папки Picasa (`Picasa/Колажі`, `Picasa/Тло`, `Picasa/Screen Captures`, `Picasa/Відео`, `Picasa/Експортовані відеозаписи`). `Exported Pictures` — папка, створена командою Export (§9.1) | ✅ / 📚 |
| `date` | `43364.530266` | Дата папки у форматі **OLE Automation Date**, записується як `%f` (§5.3) | ✅ / 📚 |
| `description`, `location` | — | Опис/місце папки | ❔ |

Секція `[Picasa]` необов'язкова: у 106 із 199 непорожніх файлів її немає.

### 2.2. `[.album:<token>]` — визначення альбому

```ini
[.album:c9ea9fa67022f38a3c771894d2a8a468]
name= Птахи
token=c9ea9fa67022f38a3c771894d2a8a468
date=2018-10-23T15:33:29+03:00
```

| Ключ | Приклад | Опис | |
| :--- | :--- | :--- | :--- |
| `token` | `c9ea9fa6…a468` | Ідентифікатор альбому, 32 hex-символи (128 біт). Завжди дорівнює частині імені секції після `.album:` | ✅ / 📚 |
| `name` | ` птицы  Украины` | Назва альбому. **Пробіли на початку/кінці й подвійні пробіли зберігаються** | ✅ |
| `date` | `2015-06-17T18:38:00+03:00` | Дата створення альбому, ISO 8601 зі зміщенням часового поясу | ✅ / 📚 |
| `location` | ` ` | Місце (у корпусі — лише один пробіл) | ✅ / 📚 |
| `description` | — | Опис альбому | ❔ |
| `name_lh` (`<name>_lh`) | — | Назва для синхронізованого з Picasa Web Albums альбому | ❔ |

Важливі властивості:

* **Альбоми — глобальні, а їхні визначення дублюються.** Альбом, що містить фото з N папок, має секцію `[.album:token]` у кожному з N файлів `.picasa.ini` (26 з 28 альбомів присутні в кількох папках). Повного списку альбомів в одному місці немає — його треба збирати об'єднанням по всіх папках за `token`. ✅
* **Секція може бути неповною:** 37 секцій містять лише `token=` без `name`/`date`. Назву треба брати з іншої папки, де той самий альбом описано повністю. ✅
* Порядок ключів не фіксований (зустрічаються `name,token,date`, `token,name,date`, `name,token,location,date`). ✅

### 2.3. `[<ім'я файлу>]` — метадані та правки окремого файлу

Ім'я секції — ім'я файлу (без шляху) у тій самій папці: `[IMG_6013.JPG]`, `[_MG_1788.JPG]`, `[Зйомка на весь екран 13.12.2020 193530.bmp]`. Ім'я може містити пробіли, крапки й кирилицю. ✅

* **Сирітські секції:** 1 310 з 4 747 секцій (≈27%) посилаються на файли, яких у папці вже немає (видалені/перейменовані). Парсер повинен це допускати й не видаляти такі записи мовчки. ✅
* Регістр імені: збігається з іменем на диску. Файлова система Windows (NTFS/FAT) не розрізняє регістр, тож зіставляти з файлами варто **без урахування регістру**. 🔶

Ключі секції файлу описано в §3.

## 4. Ланцюжок фільтрів (`filters=`, `redo=`)

### 4.1. Синтаксис

```ebnf
chain   = { filter , ";" } ;                  (* кожен фільтр закінчується ';' *)
filter  = name , "=" , params ;
params  = enabled , { "," , param } ;
enabled = "1" ;                               (* у корпусі завжди 1 *)
param   = float | hex32 | int ;
float   = [ "-" ] , digits , "." , 6*DIGIT ;  (* printf %f *)
hex32   = 1*8HEXDIG ;                         (* колір, нижній регістр *)
```

Приклад:

```
filters=crop64=1,3bb441689c65a32f;autolight=1;autocolor=1;unsharp2=1,3.000000;finetune2=1,0.000000,0.000000,0.140351,00000000,0.000000;
```

Властивості:

* Порядок значущий — це історія дій, застосовувати зліва направо. ✅ / 📚
* Фільтри **можуть повторюватися**: `unsharp2=1,0.600000;warm=1;warm=1;warm=1;unsharp2=1,0.600000;sepia=1;`. Повторне кадрування **додає** новий `crop64`, а не замінює попередній; для поточного кадру береться останній ✅ / 📚
* Числа з плаваючою крапкою — `printf("%f")`: 6 знаків після крапки, роздільник `.` незалежно від локалі. ✅
* Кольори — §5.2.
* Перший параметр — прапорець увімкнення, у корпусі завжди `1`. ✅ / 📚
* Ім'я фільтра чутливе до регістру (`Vignette` з великої). 📚

## 5. Кодування значень

### 5.1. `rect64(...)` — прямокутник ✅ / 📚

16 hex-цифр = 64-бітне число, яке розбивається на чотири 16-бітні слова `left, top, right, bottom` (старше слово — `left`). Координати нормовані [0; 1] від лівого верхнього кута.

```
rect64(33101d68ffffffff)
  left   = 0x3310 / 65535 = 0.1995
  top    = 0x1d68 / 65535 = 0.1149
  right  = 0xffff / 65535 = 1.0
  bottom = 0xffff / 65535 = 1.0
```

Перевірено на `_MG_1272.JPG` (5184×3456): кадр 4150×3059 px від (1034, 397) до правого нижнього кута.

**Дільник: 65535 чи 65536?** Джерела розходяться: [gist][gist] і PicasaPy ділять на 65536, [picasa3meta][p3m] — на `0xffff` (65535). Значення `ffff` для правого/нижнього краю, яке в корпусі трапляється при кадруванні до самого краю, дає рівно 1.0 лише при 65535. Різниця — менше 0,002 % (≤ 0,1 px на 5000 px), тож практично не важлива. Рекомендація: при читанні ділити на 65535; при записі `round(v * 65535)`. 🔶

> ⚠️ **Провідні нулі не пишуться.** Picasa форматує число через `%I64x` (MSVC-специфікатор для 64-бітного hex без доповнення). У корпусі є значення з 15 hex-цифр: `rect64(48b165fed2ef3d9)`, `crop64=1,6911ae3ce91ecbd`; такі ж є в прикладах [metaSave][metasave]. Перед розбором доповнюйте рядок нулями зліва до 16 символів (`padStart(16, '0')`) або розбирайте як одне 64-бітне число (`BigInt('0x' + hex)`) і виділяйте слова зсувами. Writer, сумісний з Picasa, має так само відкидати провідні нулі. ✅ / 📚

🔶 Координати задано відносно зображення **до** повороту `rotate=` і з урахуванням EXIF Orientation, як його показує Picasa — потребує перевірки на фото з `rotate` ≠ 0.

**Старий формат Picasa 2:** `crop=%d,%d,%d,%d,%d;` — п'ять цілих, `<не використовується>,left,top,right,bottom` у пікселях оригіналу. Picasa 3 при читанні мігрує його в `crop64`. ❔ ([PicasaPy][picasapy])

### 5.2. Кольори

| Де | Формат | Приклад | |
| :--- | :--- | :--- | :--- |
| Фільтри (`finetune2`, `Vignette`, `Neon`, `Border`, …) | hex `00RRGGBB` / `AARRGGBB`, нижній регістр, провідні нулі можуть відкидатися | `00808080`, `00ff0000`, `fff7f5f3` (gist), `ffff` (gist, `tint`) | 📚 |
| Текстові шари | **десяткове** беззнакове 32-бітне `AARRGGBB` | `4294967295` = `0xFFFFFFFF` (білий непрозорий), `4278190080` = `0xFF000000` (чорний), `0` = немає | ✅ |

> ⚠️ **Не плутати з Win32 `COLORREF`.** У класичному GDI (Windows XP і далі) колір `COLORREF` має розкладку `0x00BBGGRR`: червоний — у молодшому байті ([MS Learn: COLORREF][colorref]). Picasa цієї розкладки **не** використовує. Її формат відповідає GDI+ `ARGB` = `0xAARRGGBB` ([MS Learn: Gdiplus::Color][gdiplus]). Аргумент PicasaPy: нейтральні кольори з піпетки навколо сірого (`007c8080`, `00848071`) за RRGGBB відповідають напрямкам «холодніше/тепліше»; у корпусі так само `0088806b` (R > G > B — теплий). Альфа-байт у фільтрах зазвичай `00`, але gist має приклад `fff7f5f3`. Тому парсер має ігнорувати альфа-байт і доповнювати значення нулями зліва до 8 цифр.

### 5.3. Дати

| Де | Формат | Приклад | Розшифровка |
| :--- | :--- | :--- | :--- |
| `[Picasa] date` | **OLE Automation Date** (`DATE`/`VT_DATE`), записується `%f` | `43364.530266` | 2018-09-21 12:43:35 ✅ / 📚 |
| `[.album:…] date` | ISO 8601 з часовим поясом | `2018-10-23T15:33:29+03:00` | ✅ / 📚 |

OLE Automation Date — стандартний тип COM/OLE Automation (Windows XP: `oleaut32.dll`, `VariantTimeToSystemTime` / `SystemTimeToVariantTime`). Ціла частина — кількість діб від опівночі **30 грудня 1899**, дробова — частка доби ([MS Learn: DateTime.ToOADate][oadate], [Eric Lippert: VT_DATE][lippert], [Old New Thing][oldnewthing]). Часового поясу немає — це **локальний час** машини, на якій писали файл.

Те, що це локальний час, перевірено перехресно (§9.1): у папці експорту `date=39669.477222` = 2008-08-09 **11:27:11**. Сусідній `Thumbs.db` фіксує створення мініатюр о 2008-08-09 **08:27:26 UTC** (`FILETIME`). Різниця рівно 3 години — літній час Києва (UTC+3). ✅

| Тип часу у файлах | Зона | Де трапляється |
| :--- | :--- | :--- |
| OLE `DATE` (`%f`) | локальна | `[Picasa] date` |
| ISO 8601 зі зміщенням | явна | `[.album:…] date` |
| `FILETIME` (hex, little-endian) | UTC | `moddate` (§9.2), каталог `Thumbs.db` (§9.3) |

Конвертація: `new Date(Date.UTC(1899, 11, 30) + value * 86400000)` — результат читати як «настінний» локальний час без зони (UTC-компоненти `Date` = локальні компоненти).

> Для від'ємних значень (дати до 1899-12-30) дробова частина в OLE DATE рахується за модулем: `-1.25` = 29.12.1899 06:00, а не 28.12 18:00. Для фотоархіву неактуально, але для коректності конвертера варто знати.

## 6. Текстові шари (`text=`) ✅

Найскладніше поле: довжинно-префіксований формат, бо сам текст може містити `;`. Ні gist, ні picasa3meta його не розшифровують. Нижче — власний аналіз корпусу, частково підтверджений PicasaPy.

```
text=2;148;36;пяденица  пятнистая;Arial;0.436478,0.682873,0.019354,0.000000;v1,4294967295,0,128.000000,1.000000,0.000000,1.000000,700,0,49152;;137;25;Pseudopanthera  macularia;Arial;0.424134,0.710023,0.019354,0.000000;v1,4294967295,0,128.000000,1.000000,0.000000,1.000000,400,0,49160;;
textactive=1
```

### 6.1. Структура

```ebnf
text   = count , ";" , count * layer ;
layer  = recLen , ";" , record , ";" ;
record = txtLen , ";" , txt , ";" , font , ";" , geom , ";" , style , ";" ;
```

* `count` — кількість шарів (1…4 у корпусі).
* `recLen` — довжина `record` **у байтах UTF-8**: від першої цифри `txtLen` до `;` після `style` включно. Перевірено на 518 із 520 шарів (решта 2 містять екранування, §6.3). Після `record` іде ще один `;`-роздільник — звідси `;;` у кінці кожного шару.
* `txtLen` — довжина тексту **у байтах UTF-8** (`Инга` → 8). Рахується по *розекранованому* тексту (§6.3). 📚
* `txt` — сам текст; читати рівно `txtLen` байтів, **не шукати `;`**.
* `font` — ім'я шрифту (`Arial`, у gist — `Aharoni`), як `LOGFONT.lfFaceName`.

### 6.2. `geom` і `style`

`geom` = `x, y, size, angle`:

| Поле | Приклад | Опис | |
| :--- | :--- | :--- | :--- |
| `x`, `y` | `0.436478, 0.682873` | Позиція, нормована 0…1 від лівого верхнього кута (центр блоку чи точка прив'язки — невідомо) | 📚 / 🔶 |
| `size` | `0.019354` | Розмір шрифту відносно **висоти** зображення | 📚 |
| `angle` | `-1.570796` | Кут у **радіанах** (-π/2 = -90°; зустрічаються -π, -3π/2) | ✅ / 📚 |

`style` = `v1, fillColor, outlineColor, p3, p4, outlineWidth, p6, weight, p8, flags`:

| # | Приклад | Опис | |
| :--- | :--- | :--- | :--- |
| 0 | `v1` | Версія формату стилю | ✅ |
| 1 | `4294967295` | Колір заливки тексту, `AARRGGBB` десятково (GDI+ ARGB) | ✅ / 📚 |
| 2 | `0` / `4294967295` | Колір обведення, `AARRGGBB` (`0` — без обведення) | 📚 |
| 3 | `128.000000` | Завжди 128 (і в gist теж) | 🔶 |
| 4 | `1.000000` | Завжди 1 | 🔶 |
| 5 | `0.000000`…`0.5` | Товщина обведення (у gist `0.364486` при ненульовому обведенні) | 📚 |
| 6 | `1.000000` (рідко `0.101563`; у gist `0.878906`) | Ймовірно, непрозорість. `0.878906` ≈ 225/256 — схоже на 8-бітну альфу | 🔶 |
| 7 | `400` / `700` | Товщина шрифту = Win32 `LOGFONT.lfWeight`: `FW_NORMAL` = 400, `FW_BOLD` = 700 ([MS Learn: LOGFONT][logfont]) | ✅ / 📚 |
| 8 | `0` / `1` / `2` (у gist `258`) | Значення `258` = `0x102` спростовує гіпотезу «просто вирівнювання». Схоже на бітове поле: молодший байт 0/1/2 (вирівнювання?) + прапорець `0x100` | 🔶 |
| 9 | `49152` / `49160` | Бітові прапорці: `0xC000` / `0xC008`. Біт `0x8` — ймовірно, курсив: у корпусі ним позначені латинські назви видів, які в біології пишуть курсивом | 🔶 |

### 6.3. Екранування

Переведення рядка в тексті записується як HTML-сутність `&#010;` (`&#010;златка  березовая&#010;dicerca  furcata`). У `txtLen` кожна `&#010;` рахується як **1 байт** (`\n`), тому парсер має читати текст, розекрановуючи на льоту, а не просто відрізати `txtLen` байтів. ✅ (2 шари в корпусі). Інші сутності (напр. `&#059;` для `;`) — ❔.

## 7. Обличчя та контакти ❔

У корпусі відсутні; опис за [gist][gist] (з коментарями), [picasa3meta][p3m], [metaSave][metasave] і [PicasaPy][picasapy].

```ini
[Contacts2]
b8e4117cf1d6615b=Roy Avery;;
[IMG_0042.jpg]
faces=rect64(579922efa1cce2aa),b8e4117cf1d6615b;rect64(502f02655e191250),ffffffffffffffff
```

* **`faces=`** — пари `rect64(<hex>),<contactId>`, розділені `;`. `contactId` — 64-бітний hex (`%I64x`, тож провідні нулі теж можуть бути відсутні).
  * `ffffffffffffffff` — обличчя, позначене як «ігнорувати» / непідтверджене.
  * Розпізнані, але не названі обличчя в `.picasa.ini` **не пишуться** — вони є лише в центральній базі `db3`.
* **`[Contacts2]`** — локальні контакти: `<contactId>=<full_name>;<email>;<gaia_id>`. Рівно 3 поля, інакше Picasa відкидає запис з помилкою `Cannot restore .ini entry for contact, %llx, unexpected number of tokens in string.` ([PicasaPy][picasapy]). Порожні email/gaia дають `Ім'я;;`.
* **`[Contacts]`** — контакти облікового запису Google: `<contactId>=<user>_lh,<hex_id>`.
* Повні імена й email контактів Picasa також тримає в `contacts.xml` центральної бази. Якщо `[Contacts2]` у папці немає, ім'я можна взяти лише звідти ([picasa3meta][p3m], [imageo][imageo]).

### 9.2. `.picasaoriginals/.picasa.ini` — стан збережених оригіналів ✅

| `textactive` | `0` | Текстових шарів не було |

Особливості:

* `backuphash` і `crop` тут відсутні; натомість є `moddate`/`width`/`height`, яких немає в жодному з 201 основних файлів. Схоже, це окремий набір ключів «метаданих оригіналу». 🔶
* Сам збережений `DSC05378.JPG` у батьківській папці вже видалено, а батьківського `.picasa.ini` немає. Оригінал у `.picasaoriginals/` при цьому лишився, тож парсер має вміти показати оригінал без «основного» файлу.
* Декодування `moddate`:

  ```ts
  const ft = Buffer.from(hex, 'hex').readBigUInt64LE(0);       // 100-нс інтервали від 1601-01-01 UTC
  const ms = Number(ft / 10000n) - 11644473600000;             // → Unix ms
  ```

### 9.3. `Thumbs.db` — кеш мініатюр Windows XP ✅

Файл не належить Picasa: його створює Провідник Windows XP (у режимі «Мініатюри») у кожній переглянутій папці. Починаючи з Vista мініатюри зберігаються централізовано (`thumbcache_*.db`), тож `Thumbs.db` у папці — ознака того, що архів побував на XP.

Структура, перевірена на двох файлах:

* Контейнер — **OLE Compound File Binary** (CFB, «Composite Document File V2»), той самий, що в `.doc`/`.xls`. Читається, наприклад, `olefile` (Python).
* Потік `Catalog`: заголовок 16 байтів — `u16 headerLen=16, u16 version=7, u32 count, u32 width=96, u32 height=96`. Далі `count` записів: `u32 recLen, u32 id, u64 FILETIME, UTF-16LE ім'я файлу\0`.
* Мініатюри лежать в окремих потоках, названих **id у десятковому записі задом наперед** (`id=100` → потік `001`). Кожен потік: 12-байтний заголовок (`u32 12, u32 1, u32 jpegLen`) + JPEG (`ff d8 ff e0`).
* Перший запис каталогу має ім'я-GUID `{A42CD7B6-E9B9-4D02-B7A6-288B71AD28BA}` і, ймовірно, позначає саму папку. 🔶
* `FILETIME` у каталозі — UTC; він допоміг підтвердити, що `[Picasa] date` — локальний час (§5.3).

Для Paloma: `Thumbs.db` пропускати при скануванні й не показувати як медіафайл. Мініатюри 96×96 надто малі, щоб їх перевикористовувати.

## 10. Рекомендації для парсера Paloma

1. Шукати в папці `.picasa.ini` **і** `Picasa.ini` (без урахування регістру); у `.picasaoriginals/` — окремий `.picasa.ini` зі станом оригіналів (§9.2), його не змішувати з основним.
2. Читати файл як байти → UTF-8 (fallback — системна ANSI-кодова сторінка) → розбивати за `\r\n` (з fallback на `\n`). Порожній файл = відсутність даних.
3. Секції `[Picasa]`, `[.album:*]`, `[Contacts*]`, `[encoding]`, `[photoid]` визначати за ім'ям; решта — секції файлів.
4. Значення **не тримити**; невідомі ключі, секції й фільтри зберігати сирими для round-trip.
5. При дублікатах ключів брати перше входження (як у Windows INI).
6. `rect64`: `padStart(16, '0')` або `BigInt`; ділити на 65535.
7. `crop=` ігнорувати при рендері — джерело істини — останній `crop64` у `filters`.
8. Альбоми будувати глобально: об'єднувати `[.album:token]` з усіх папок, брати першу повну назву; членство — з `albums=` секцій файлів.
9. Секції без файлу на диску не відкидати. Зіставляти перейменовані файли за `backuphash` **не можна** — це не хеш вмісту.
10. `text=` розбирати за довжинами в байтах, а не через `split(';')`.
11. Для JPEG підпис і теги читати з IPTC/XMP самого файлу, а не з `.picasa.ini`.
12. При записі: CRLF, без BOM, `%f` для чисел, hex у нижньому регістрі без провідних нулів, `;` після кожного фільтра, `rotate(0)` писати явно.
13. Файли `Thumbs.db`, `desktop.ini`, `.DS_Store` ігнорувати при скануванні.

## 11. Відкриті питання

* **`backuphash`:** перевірити формулу PicasaPy (XOR 16-бітних слів OLE DATE часу запису) — порівняти з `mtime` файлу `.picasa.ini` для останньої відредагованої фотографії.
* Точна семантика параметрів ефектів Picasa 3.9 (`PencilSketch`, `Neon`, `Border`, `MuseumMatte`, `Soften`, `PicnikGrain`) — потрібні контрольні правки з відомими положеннями повзунків або `filterdesc.xml` з exe (PicasaPy: `docs/specs/filters-decoded.md`).
* Чи прив'язані `rect64` і `text` до орієнтації до/після `rotate` та EXIF Orientation.
* Поля 3, 4, 6, 8, 9 стилю тексту; чи `x, y` — центр блоку.
* Чи пише Picasa `.picasaoriginals/.picasa.ini` при кожному Save, і чи `moddate` — це mtime оригіналу саме на момент Save (потрібно більше зразків).
* Чи бувають на неанглійських Windows файли в ANSI-кодуванні замість UTF-8.
